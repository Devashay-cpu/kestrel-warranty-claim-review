# Phase 1 decisions (data prep, leakage, validation)

| # | Topic | Decision | Why |
|---|---|---|---|
| 1 | Duplicates | 681 claim_ids appear twice (resubmits). Keep the FIRST submission per claim_id; label = max of non-null labels (0 conflicts found). | Resubmits are identical copies; keeping both double-counts and lets a claim sit in train and validation. Test has no duplicate ids, so "is resubmission" is not usable as a feature. |
| 2 | Blank labels | 215 blank rows = 202 unique claims, all `source=crm`. Removed from training, evaluation and partner label history. Saved to `artifacts/train_undecided_blank_labels.csv`. They still count in label-free volume features (they are real claims). | Blank = undecided, not "not fraud". Treating as 0 would teach the model that unresolved cases are clean. Blank rate is flat (~3%/month, no recency bump), so no evidence they are biased towards recent weeks; this is an assumption. |
| 3 | Legacy zeros | Legacy Zoho rows have no blanks (undecided were exported as 0). Kept as 0, flagged as label noise in the report. | Cannot be separated; noise only lowers the apparent fraud rate. |
| 4 | Injected text | 5 rows / 4 claim_ids contain instruction text in `claim_description`. Treated as untrusted data; those claims excluded from training (`artifacts/train_excluded_injected_text.csv`). Free text is only ever mapped to 12 known categories (else `other`). | Not followed. Same rule protects the API. |
| 5 | Leakage | `is_fraud` (target), `claim_id` (time proxy), `source` (confounded with time; test is all crm), `n_submissions` (absent in test), `regime_post_may` (constant in test), raw free text, `partner_id`, `onboarded_date`, `city` are never model inputs (`features.FORBIDDEN`, enforced by test). | |
| 6 | May-2026 regime | `is_small` (< Rs 2,000) and `auto_approved` (= small AND date >= 1 May 2026) derived from policy s5. `regime_post_may` kept as metadata only. In test 77% of claims are small and 100% of those are uninspected; in labelled train only ~16% are uninspected. Validation therefore includes a post-May fold; Phase 2 should weight/restrict to recent data and report the post-May fold as the headline. | Fraud moved into small, uninspected claims after May (3.2% vs 0.5% pre-May). |
| 7 | Partner history | Label-derived: counts and empirical-Bayes rates (all-time and last 90 days) using only claims submitted <= t - 14 days (rolling, for training rows) or <= a fixed cutoff (frozen, for validation/test rows). Label-free: partner claims in prior 7/30 days and small-claim share, strictly earlier claims only. Partner age is available as an OPTIONAL group (univariate AUC 0.49, i.e. no blanket "new partner" signal). | Matches how the system would run: labels arrive late, test is scored with history frozen at export. |
| 8 | Lag assumption | LAG_DAYS = 14. Blank rate by week shows no recency effect, so true investigation lag is unknown. Conservative and parameterised in `config.py`. | |
| 9 | Validation | 3 time folds, embargo = LAG_DAYS, no random splits: A (Feb-Apr, old regime, sanity), B (May-Jun, test-like, history frozen at start, 36 fraud), C (Jun only, 22 fraud). Top-K = 40 per 750 claims. Headline = B. | Only ~36 post-May positives: intervals will be wide. |
| 10 | Timestamps | `submitted_at` is IST; there is no resolution-event column, so the Zoho UTC quirk (policy s9) does not apply to this data. Documented, no shift applied. | |
| 11 | Serial | Normalised (strip, remove hyphen, upper-case). Format / reuse features are OPTIONAL group `serial` (audit: no lift). | |

Known gaps: undecided cases may differ in fraud rate; EB strength (20) and lag (14 d) are not tuned; test partner history is staler (up to 3 months) than in validation folds B/C only by design of "frozen".
